# PiPy Architecture

## A Self-Organizing Raspberry Pi Compute Fabric

**Status:** architectural foundation

PiPy is a self-organizing distributed-computing fabric intended to make a group of Raspberry Pi computers behave as one cooperative compute system with minimal operator involvement. Every node runs the same software. Nodes discover one another, establish trust, form or join a cluster, share cluster state, elect temporary coordination roles, claim work, execute work, recover from failure, and emit externally consumable status without requiring a separately configured controller, scheduler, database, or dashboard.

The reference workload is arbitrary-precision computation of π. The architecture is deliberately not specific to π. π is the first workload used to exercise and demonstrate a general distributed-work model built around divisible work units, leases, deterministic result validation, reduction, replicated state, and heterogeneous compute capacity.

The core operating principle is:

> Install PiPy on a set of Raspberry Pis, start PiPy, and the machines organize themselves into a compute fabric.

PiPy should require explicit trust establishment, but not manual topology construction. A cluster has no permanently special machine. One node may temporarily coordinate consensus and scheduling, but every healthy node remains a compute node, a discovery participant, a state replica, and a candidate for future leadership.

---

# 1. Design Goals

PiPy is designed around the following goals.

## 1.1 Self-organization

A new installation can start alone, remain useful alone, discover peers later, and grow into a cluster without changing software roles or reinstalling components.

The cluster must tolerate:

- nodes starting in arbitrary order;
- nodes appearing and disappearing;
- mixed Raspberry Pi generations and capacities;
- temporary loss of the current coordinator;
- Wi-Fi reassociation and address changes;
- restarts;
- partial work loss;
- duplicate messages;
- delayed messages;
- stale membership observations.

## 1.2 One node type

There is no controller package and worker package.

Every PiPy node can:

- discover peers;
- authenticate peers;
- participate in membership;
- hold replicated cluster state;
- participate in leader election;
- coordinate work when elected;
- execute work;
- verify work;
- emit telemetry;
- admit new nodes when policy permits.

"Coordinator" is an elected role with a bounded term or lease. It is not a machine identity.

## 1.3 Explicit trust, automatic operation

Discovery is automatic. Trust is not.

PiPy must not treat “a machine answered a BLE beacon” as sufficient authorization to join a cluster. Trust originates from cluster bootstrap material created by an already trusted PiPy installation.

## 1.4 Local-first operation

A PiPy cluster should continue operating without Internet access after required software is installed.

Internet access may be useful for package installation, updates, or optional external reporting, but it is not part of cluster correctness.

## 1.5 Purpose-built distributed computing

PiPy is not intended to become a general container orchestrator, remote shell, or Kubernetes replacement.

Its distributed-computing abstraction should stay small and explicit:

- jobs;
- work units;
- leases;
- results;
- dependencies;
- reductions;
- verification;
- cancellation;
- replicated job state.

## 1.6 Observable without coupling

The cluster must not require a dashboard to function.

Nodes emit status using UDP broadcast or multicast. External observers may consume this telemetry without becoming participants in cluster consensus.

A separate package such as `pipy-dash` may listen to broadcasts, populate SQLite, and present a dashboard. The cluster must not depend on it.

## 1.7 Heterogeneous scaling

A Pi Zero and a Pi 5 are both valid nodes. Work distribution should adapt to measured throughput rather than assume equal machines.

## 1.8 Recoverability over perfection

PiPy assumes individual boards, processes, links, and work units can fail. Correctness comes from leases, replicated state, deterministic work identities, result verification, and retry rather than from assuming failure will not occur.

# 2. Terminology

## Node

One running PiPy installation on one host.

## Lone wolf

A healthy PiPy node that currently forms a cluster of one.

A lone wolf is not an error state. It is the smallest valid cluster.

## Cluster

A set of mutually trusted PiPy nodes sharing one cluster identity, membership state, unity key generation, replicated job state, and consensus history.

## `imapipy` identity

The persistent asymmetric identity key pair generated by the first PiPy node when it creates a new cluster.

The name refers to the cluster-root identity material, not to a universal PiPy vendor key. There is no static “I am PiPy” key shared by all installations.

## Node identity

A persistent asymmetric identity key pair unique to one PiPy installation.

Every node has its own node key pair.

## Unity key

A symmetric cluster membership key for one key generation. It is shared only with authenticated members and is rotated according to cluster policy.

The unity key is not the `imapipy` private key and must never be used as a substitute for node identity.

## Enrollment capability

A narrowly scoped bootstrap credential generated by an existing cluster and embedded in or fetched by `makemeapipy.sh`. It authorizes creation/admission of a new PiPy member under defined constraints.

## Coordinator

The node currently holding the cluster’s consensus leadership role. The role is temporary and transferable.

## Work unit

A deterministic, addressable piece of a job that can be leased to and executed by a node.

## Lease

A time-bounded claim allowing one node to treat a work unit as its assigned responsibility. Expired work may be reassigned.

## Result

The output of a work unit plus metadata sufficient to establish what was computed, by whom, under which algorithm/version/input identity, and with what verification evidence.

# 3. First Run and Cluster Genesis

PiPy has no static global trust key.

When the first installation runs and does not discover or authenticate any existing PiPy cluster, it enters lone-wolf mode and creates a new cluster.

The first-run sequence is:

```text
PiPy starts
    |
    +-- create persistent node identity key pair
    |
    +-- advertise and listen for PiPy BLE discovery
    |
    +-- attempt local authenticated peer discovery for bounded bootstrap interval
    |
    +-- no trusted cluster found
            |
            +-- create new cluster identifier
            +-- generate imapipy root identity key pair
            +-- generate initial unity key generation
            +-- initialize replicated state as one-member cluster
            +-- become consensus leader for term 1
            +-- begin compute/service operation
            +-- generate makemeapipy.sh
```

The cluster identifier should be random and globally collision-resistant, for example a UUIDv7 or 128-bit random identifier.

The first node’s node identity and the cluster `imapipy` identity are distinct. This distinction matters because leadership can later move to another node without moving or sharing a machine-specific private identity.

The cluster root private key should be protected at rest and used only for cluster-root operations that truly require it. Routine node-to-node traffic should use node identities and ephemeral session keys, not repeated use of the root private key.

---

# 4. `makemeapipy.sh`

The first cluster creates a bootstrap script named:

```text
makemeapipy.sh
```

The operator runs this script on each additional Raspberry Pi that should become eligible to join the cluster.

The script serves two purposes:

1. install or configure PiPy on the new host;
2. transfer a bounded cluster enrollment capability establishing which cluster this installation is allowed to join.

It must **not** contain the `imapipy` private key.

It should not contain a reusable cluster-wide permanent secret when a narrower credential will suffice.

A suitable model is:

```text
makemeapipy.sh
    |
    +-- installs PiPy through supported package/install path
    +-- creates local service account/state directories
    +-- starts PiPy enrollment/bootstrap command
    +-- provides:
          cluster_id
          cluster root public key / fingerprint
          one-time or bounded enrollment token
          bootstrap policy/version
          optional discovery/contact hints
          optional encrypted network bootstrap material
```

The enrollment token should normally be:

- single-use or use-count limited;
- time limited where practical;
- bound to one cluster;
- cryptographically signed or MAC-protected;
- revocable before use if cluster state supports revocation;
- unsuitable for deriving the unity key directly.

On first run of the new node, PiPy generates its own node identity key pair locally. The private node key never needs to leave that machine.

The enrollment capability allows that new node identity to request cluster admission.

A future convenience command might be:

```bash
pipy make-node-script > makemeapipy.sh
```

or:

```bash
pipy enrollment create --script makemeapipy.sh
```

The generated script is an administrative artifact and should clearly report its expiration/use policy when created.

# 5. Why Discovery Still Exists

`makemeapipy.sh` makes it possible to pre-authorize a machine without relying on discovery. This does not make discovery redundant at the architectural level.

The script answers:

> Which cluster am I permitted to join?

Discovery answers:

> Which eligible PiPy peers are physically/network-locally reachable right now, and how do I contact them?

Every node continues to advertise and listen for PiPy discovery beacons after joining.

BLE provides an especially useful local bootstrap plane because it does not require the new node to already know the cluster’s IP topology.

Discovery is also valuable when:

- nodes reboot with new DHCP addresses;
- the current leader changes;
- a node has cluster credentials but no remembered reachable IP address;
- the cluster is moved to a different local network;
- a node was provisioned earlier and is only powered on later;
- Wi-Fi credentials are to be provisioned only after authenticated local admission.

Thus PiPy intentionally has both explicit enrollment and automatic discovery.

# 6. BLE Discovery Plane

Every running PiPy node advertises a BLE service beacon and scans for the same service.

The BLE beacon must contain only public, non-secret discovery information. A typical advertisement may include:

```text
protocol family/version
truncated cluster ID or cluster hint
node discovery nonce
capability flags
admission-possible flag
rotating ephemeral discovery identifier
```

It must not contain:

- unity keys;
- Wi-Fi credentials;
- node private keys;
- cluster-root private material;
- reusable authentication secrets.

BLE discovery initiates a challenge/response admission or reconnection exchange.

A node detecting another PiPy advertisement does not immediately trust the peer. It begins authenticated negotiation.

# 7. Admission and the Four-Way Handshake

PiPy uses a four-stage logical admission handshake. The architecture defines the security properties, not a requirement to invent novel cryptography.

The implementation should use established cryptographic primitives and, where suitable, an established authenticated key-exchange construction such as a Noise framework pattern rather than implementing ad hoc encryption.

The logical sequence is:

## Message 1 — Discover / challenge

An existing node sends:

- protocol version;
- cluster identifier/fingerprint;
- fresh random challenge;
- ephemeral key-exchange public material;
- its node identity certificate/assertion;
- current membership epoch.

Conceptually:

> Are you an authorized candidate for this PiPy cluster?

## Message 2 — Candidate proof

The candidate responds with:

- its fresh locally generated node public identity;
- proof of possession of its private node key;
- the bounded enrollment capability from `makemeapipy.sh` or another authorized admission path;
- response to the fresh challenge;
- its ephemeral key-exchange material;
- candidate capabilities.

This proves that the candidate is not merely replaying a BLE beacon and that it possesses valid cluster admission authority.

## Message 3 — Cluster acceptance

After validating the candidate and committing membership through the cluster’s authoritative membership mechanism, the admitting side returns over the newly authenticated encrypted session:

- accepted node identity and membership record;
- current membership epoch;
- current unity-key generation and unity material wrapped for the authenticated session;
- cluster network/service parameters;
- coordinator/contact set;
- optional Wi-Fi credentials, if configured for cluster distribution;
- initial state synchronization instructions.

Wi-Fi credentials, if distributed, appear only after an authenticated encrypted channel exists.

## Message 4 — Confirmation

The new member confirms:

- successful installation of cluster membership state;
- possession of the current unity-key generation;
- successful state/bootstrap receipt;
- optional transition to Wi-Fi connectivity;
- final transcript authentication.

The cluster then marks the admission complete.

The four messages form one authenticated transcript. Nonces, cluster ID, protocol version, ephemeral keys, node identities, and membership epoch should all be transcript-bound to prevent substitution/replay across clusters or generations.

# 8. Key Hierarchy

PiPy separates identity, admission, cluster membership, and session encryption.

## 8.1 Cluster root identity (`imapipy`)

Persistent asymmetric key pair created when a new cluster is born.

Uses include:

- establishing the long-lived identity of the cluster;
- signing cluster-root metadata where necessary;
- validating enrollment authorities or trust anchors;
- anchoring continuity across leader changes.

It is not used to encrypt ordinary compute traffic directly.

## 8.2 Node identity key

Persistent asymmetric key pair generated locally by every PiPy node.

Uses include:

- node identity;
- proof of possession;
- authenticated peer sessions;
- signed node statements where necessary;
- membership records.

## 8.3 Enrollment capabilities

Short-lived or limited-use admission credentials.

These authorize a new node identity to request membership. They should not grant indefinite ability to impersonate existing members.

## 8.4 Unity key

Symmetric secret shared among current cluster members.

The unity key identifies membership in a particular generation and can be used for efficient cluster-wide message authentication/encryption where group semantics are appropriate.

The unity key should have a monotonically increasing generation number.

Key rotation should occur at least when:

- an administrator explicitly requests rotation;
- a node is expelled for security reasons;
- compromise is suspected;
- policy-defined age/use thresholds are crossed.

A graceful temporary node failure does not necessarily require immediate unity-key rotation; removal versus temporary unavailability must be distinct membership concepts.

## 8.5 Pairwise session keys

Ephemeral keys derived from authenticated key exchange between peers.

Uses include:

- admission;
- sensitive state synchronization;
- pairwise RPC/transport security;
- delivery of new unity-key generations.

Compromise of one session key should not reveal long-term identity private keys.

# 9. Network Bootstrap

A PiPy cluster may optionally be configured with network credentials that it is allowed to provision to admitted nodes.

This feature is useful when a new Pi is physically nearby and Bluetooth-reachable but not yet joined to the cluster’s Wi-Fi network.

The rule is strict:

> Network credentials are cluster secrets and are delivered only after candidate identity and enrollment authority have been authenticated and an encrypted pairwise session has been established.

Possible flow:

```text
new node
  | BLE
  v
existing member
  | authenticated four-way admission
  v
encrypted session
  |
  +-- membership material
  +-- Wi-Fi SSID/security parameters/credential
  v
new node associates to Wi-Fi
  |
  +-- verifies cluster peers on IP transport
  +-- completes state synchronization
```

The network credential is operational configuration, not the root of PiPy trust. A machine knowing the Wi-Fi password is not thereby a PiPy member.

# 10. Transport Planes

PiPy intentionally separates different classes of traffic.

## 10.1 Discovery/admission plane

Primarily BLE for local discovery and bootstrap.

Purpose:

- peer detection;
- cluster hinting;
- authenticated admission initiation;
- recovery of contact information;
- optional secure network provisioning.

## 10.2 Cluster control plane

Authenticated IP networking between members.

Purpose:

- consensus;
- membership state;
- job creation/cancellation;
- work leases;
- result publication;
- key-generation updates;
- authoritative state synchronization.

This plane requires reliable delivery semantics appropriate to each protocol operation.

## 10.3 Compute data plane

Transfer of work input, intermediate result references, result payloads, or chunk data.

Large payloads should not be forced through the consensus log. The log should carry identities, hashes, metadata, leases, and authoritative transitions. Large immutable data can use direct authenticated transfer and content-addressed storage semantics.

## 10.4 Telemetry plane

UDP broadcast or multicast emitted periodically by nodes.

Purpose:

- human dashboards;
- monitoring;
- historical collection;
- ad hoc tools;
- benchmarking visualization.

Telemetry is explicitly non-authoritative. Lost UDP status packets do not alter cluster correctness.

# 11. Membership and Replicated State

Cluster status required for correctness is replicated across members.

PiPy should distinguish:

1. **authoritative replicated state** required to resume or coordinate computation;
2. **derived/local state** that can be reconstructed;
3. **telemetry** that can be lost.

Authoritative replicated state includes at minimum:

```text
cluster_id
cluster public identity/fingerprint
membership epoch
known members and member status
current consensus term/leader
unity-key generation metadata
active job identities
job definitions and algorithm versions
work graph/frontier identities
lease ownership and expirations
accepted result identities/hashes
reduction state/checkpoints
job completion/cancellation state
```

It does not necessarily include every byte of every intermediate result in the consensus log.

---

# 12. Consensus and Coordinator Election

PiPy needs one authoritative ordering for operations such as membership changes, job acceptance, lease grants, result acceptance, and coordinator transitions.

A small-cluster consensus algorithm in the Raft family is a good conceptual fit:

- one elected leader at a time;
- monotonically increasing terms;
- replicated ordered log;
- majority commit semantics;
- automatic reelection;
- followers retain complete authoritative state;
- snapshots can compact old log history.

The architecture does not require a bespoke Raft implementation. A maintained package should be preferred if it meets PiPy’s needs.

The elected leader is called the coordinator in user-facing descriptions.

Coordinator duties include:

- serializing authoritative state transitions;
- granting work leases;
- accepting/rejecting result commits;
- maintaining the canonical available-work frontier;
- driving membership changes;
- initiating unity-key rotations;
- publishing cluster-level summaries.

The coordinator also computes work like every other node. Coordination should consume only the resources needed for control-plane correctness.

If the coordinator fails:

```text
heartbeats cease
    |
followers begin election after randomized timeout
    |
new term established
    |
new coordinator elected
    |
expired/unconfirmed leases become reclaimable
    |
computation continues
```

No external operator intervention should normally be required.

---

# 13. Split-Brain and Partition Behavior

PiPy must prefer correctness over maximizing work during ambiguous network partitions.

A partition without a consensus majority cannot commit new authoritative cluster transitions.

Nodes in a minority partition may continue safe local activities only when those activities cannot create conflicting committed state. They may retain or complete already leased deterministic work and hold the result locally, but result acceptance should wait until a majority-backed coordinator is reachable.

When connectivity returns:

- consensus state reconciles according to the authoritative log;
- uncommitted conflicting leadership is discarded;
- still-valid deterministic results may be submitted;
- expired work may have been duplicated, which is acceptable if result identity makes acceptance idempotent.

Duplicate computation wastes compute but must not corrupt state.

# 14. Work Model

PiPy’s distributed-compute abstraction is intentionally small.

A job is represented as a deterministic work graph or reducible frontier.

The conceptual interface is:

```python
class PiPyJob:
    def create(self, specification) -> "JobState": ...
    def split(self, state, target_cost) -> list["WorkUnit"]: ...
    def compute(self, unit) -> "WorkResult": ...
    def verify(self, unit, result) -> "Verification": ...
    def combine(self, state, accepted_results) -> "JobState": ...
    def complete(self, state) -> bool: ...
    def finalize(self, state) -> object: ...
```

The actual public API may evolve, but the architecture preserves these roles.

A workload plugin must clearly define:

- deterministic job identity;
- algorithm/version identity;
- input identity;
- work-unit identity;
- execution requirements;
- result encoding;
- verification strategy;
- combination/reduction semantics;
- completion condition.

The cluster scheduler should not contain π-specific logic.

# 15. Work Units

A work unit is immutable once issued.

Recommended metadata:

```text
job_id
work_unit_id
algorithm_id
algorithm_version
input_hash
range/path/partition descriptor
dependency identities
estimated_cost
required capabilities
creation epoch
```

A work-unit ID should be deterministic when practical so the same logical computation is recognized as the same unit across retries.

This enables:

- idempotent result acceptance;
- duplicate-work detection;
- content caching;
- deterministic recovery;
- auditability.

---

# 16. Leased Work Claiming

PiPy should not model work distribution as a leader permanently pushing tasks to workers.

Nodes claim work according to available capacity.

Conceptually:

```text
node -> coordinator:
    capacity report + request for work

coordinator:
    selects eligible available units
    commits lease grants

node:
    executes leased units
    periodically renews lease if appropriate
    submits result
```

A lease contains:

```text
job_id
work_unit_id
lease_id
node_id
lease_start
lease_deadline
term/epoch
```

If a node disappears, its leases eventually expire and the corresponding work returns to the available frontier.

The old node may later reconnect and submit a late result. The coordinator decides idempotently:

- accept it if that work is still unresolved and validation passes;
- treat it as duplicate if an equivalent result is already committed;
- reject it if job state makes it obsolete.

No special cleanup procedure is required merely because a worker vanished.

---

# 17. Adaptive Scheduling

PiPy should learn actual node throughput.

Hardware model names are useful hints, not scheduling truth.

Each node maintains rolling measurements such as:

```text
work type
units completed
wall-clock compute time
CPU utilization
memory pressure
thermal throttling state
recent failures
network transfer cost
```

The scheduler can estimate normalized capacity per workload type.

For example:

```text
node A: 0.22 normalized units
node B: 0.74
node C: 1.00
node D: 1.15
```

A faster node naturally receives or requests larger/more numerous leases.

Work chunking should aim for a useful lease duration rather than a fixed item count. Too-small units waste control-plane overhead; too-large units increase recovery cost when a node fails.

The target unit duration can adapt from observed cluster conditions.

---

# 18. Result Verification

Distributed computation should not equate “a node returned bytes” with “the work is correct.”

Each workload defines a verification strategy appropriate to its cost and mathematical properties.

Possible strategies include:

- deterministic recomputation of inexpensive checks;
- internal invariants;
- modular checks;
- hashes over canonical encodings;
- redundant computation of selected units;
- cross-node spot checks;
- hierarchical verification during reduction.

PiPy should support configurable verification levels where workloads permit it.

The result record should include:

```text
work_unit_id
result_hash
result encoding/version
producer node_id
execution metadata
verification status/evidence
accepted term/epoch
```

# 19. Reference Workload: π

The reference π workload should use an algorithm suitable for real arbitrary-precision distributed computation rather than a Monte Carlo approximation.

A strong reference candidate is the Chudnovsky formula implemented with binary splitting.

Binary splitting decomposes the calculation into independent subranges that produce partial tuples conventionally represented as values such as `P`, `Q`, and `T`. Those partial results can be combined recursively into larger ranges until the final series value is assembled and converted to π at the requested precision.

This maps naturally onto PiPy:

```text
π job
  |
  +-- determine required Chudnovsky term range
  |
  +-- create binary-splitting leaves/subtrees
  |
  +-- lease independent subtrees to nodes
  |
  +-- compute partial P/Q/T values
  |
  +-- verify/canonicalize results
  |
  +-- reduce neighboring subtrees
  |
  +-- continue until root result
  |
  +-- final high-precision square root/division
  |
  +-- publish π artifact + verification metadata
```

Reduction work itself is schedulable. Large upper-tree multiplications can become work units rather than forcing the coordinator to perform every merge locally.

The π workload is therefore a useful full-system exercise of:

- recursive work graphs;
- independent compute;
- large integer arithmetic;
- heterogeneous scheduling;
- deterministic outputs;
- reduction dependencies;
- checkpointing;
- recovery;
- verification;
- final artifact generation.

# 20. Job State and Reduction

A job should have an explicit state machine, for example:

```text
CREATED
  -> RUNNING
  -> FINALIZING
  -> COMPLETED

RUNNING -> CANCELLING -> CANCELLED
any active state -> FAILED when unrecoverable policy condition is met
```

Work units have their own states:

```text
AVAILABLE
LEASED
RESULT_PENDING
ACCEPTED
SUPERSEDED
```

Failure of one attempt does not necessarily create a FAILED work unit. Usually the lease simply expires or the unit becomes AVAILABLE again.

Reduction dependencies should be explicit. A parent reduction is available only after required child results are accepted.

This permits the whole distributed calculation to survive coordinator changes because the reduction frontier is replicated state rather than process-local scheduler memory.

---

# 21. Data and Artifact Handling

Consensus should not become a bulk-data transport.

Small results may be included directly when efficient. Large work results should be immutable artifacts addressed by cryptographic hash or stable artifact ID.

A committed result record may say:

```text
artifact_id
sha256
size
encoding
holder set / replication hints
```

Nodes can fetch large artifacts directly from authenticated peers.

For important intermediate state, PiPy may maintain a small replication factor so failure of one node does not force expensive recomputation.

The desired replication factor can be workload- or artifact-specific.

Final job artifacts should be exportable independently of PiPy’s internal storage.

---

# 22. Node Storage

Each node maintains local persistent state sufficient to rejoin after restart.

Suggested categories:

```text
identity/
    node private/public identity
    trusted cluster root public identity

cluster/
    cluster_id
    membership snapshot
    consensus log/snapshot
    unity-key generations

jobs/
    job metadata
    local work checkpoints
    result/artifact cache

runtime/
    current leases
    performance history
    transient peer/contact cache
```

Sensitive key material should use restrictive filesystem permissions and operating-system facilities where available.

Transient runtime state should be reconstructable after process restart from authoritative replicated state plus local durable checkpoints.

---

# 23. Restart Semantics

A node restart should be routine.

On restart:

```text
load node identity
load trusted cluster identity
load last replicated snapshot/log
start BLE advertise/scan
attempt remembered IP peers
authenticate current peers
learn current term/leader/membership epoch
synchronize missing authoritative state
reconcile local leases/results
resume requesting work
```

A remembered address is only a contact hint. Trust still comes from cryptographic identity.

If the node cannot find its cluster, it remains in a disconnected-member state and continues discovery. It must not silently create a new cluster merely because its known cluster is temporarily unreachable.

Only a never-enrolled installation with no trusted cluster identity may create a new lone-wolf cluster automatically.

---

# 24. Node Loss and Removal

PiPy distinguishes:

- temporarily unreachable;
- administratively removed;
- cryptographically distrusted/expelled.

A temporarily unreachable member retains its identity in membership history and may rejoin normally.

Administrative removal prevents normal participation until readmitted.

Security expulsion should trigger unity-key rotation so the expelled node does not retain current group key material.

Outstanding leases from removed/unreachable nodes become reclaimable after policy-defined expiration.

---

# 25. UDP Status Broadcasts

Every node periodically emits a compact telemetry record using UDP broadcast or multicast on the local network.

Telemetry should be versioned and self-describing enough for independent consumers.

A conceptual record:

```json
{
  "schema": "pipy.status.v1",
  "cluster_id": "...",
  "node_id": "...",
  "term": 17,
  "coordinator": false,
  "membership_epoch": 31,
  "job_id": "...",
  "job_state": "running",
  "work_unit_id": "...",
  "node_progress": 0.73,
  "cluster_progress": 0.48,
  "throughput": 12.4,
  "throughput_unit": "work_units_per_second",
  "cpu_percent": 96.2,
  "memory_percent": 41.1,
  "temperature_c": 67.4,
  "thermal_throttled": false,
  "peer_count": 6,
  "uptime_seconds": 81233,
  "timestamp_ns": 0
}
```

Exact fields will evolve by schema version.

Status broadcasts must not contain:

- unity keys;
- Wi-Fi credentials;
- private identities;
- admission capabilities;
- sensitive workload payloads.

Telemetry authenticity may optionally be supported with a cluster-publicly-verifiable signature or separate observer key scheme, but telemetry correctness must remain separate from consensus correctness.

# 26. `pipy-dash`

Dashboarding is intentionally outside the core cluster.

A standalone observer can:

```text
UDP listener
    |
    v
normalize status packets
    |
    v
SQLite history
    |
    +-- web UI
    +-- charts
    +-- topology
    +-- per-node performance
    +-- job progress
    +-- thermal/uptime history
```

The canonical optional dashboard may be distributed separately:

```bash
pip install pipy-dash
pipy-dash
```

Other observers can exist without coordination with PiPy core:

- terminal UI;
- Prometheus exporter;
- Grafana bridge;
- logger;
- benchmarking collector;
- home-automation integration.

No observer receives scheduling authority simply by listening to telemetry.

# 27. Service Interface and CLI

The exact CLI may evolve, but the architecture suggests a small operational surface.

Examples:

```bash
pipy begin
pipy status
pipy members
pipy enrollment create --script makemeapipy.sh
pipy job submit pi --digits 1000000000
pipy job list
pipy job inspect <job-id>
pipy job cancel <job-id>
pipy key rotate
```

`pipy begin` should be idempotent in spirit: start or ensure the local PiPy service exists, create a cluster only if this installation has never been enrolled, and otherwise reconnect to its existing cluster.

Most normal multi-node use should not require users to name a coordinator or enumerate worker addresses.

# 28. Internal Service Decomposition

A single PiPy daemon can be organized into cooperating services:

```text
PiPy Node
```

# 29. Concurrency Model

PiPy is naturally event-driven.

A recommended Python control-plane model is `asyncio`:

- BLE events feed discovery/admission tasks;
- cluster sockets use async networking;
- consensus timers use async deadlines;
- lease timers are asynchronous;
- telemetry emission is periodic async work;
- state synchronization is async;
- CPU computation runs outside the event loop.

The daemon event loop must remain responsive while all CPU cores are busy.

Compute execution is a resource, not the scheduler itself.

For CPU-heavy pure Python or arbitrary-precision workloads, a process pool or explicit worker processes are generally appropriate. If a library performs heavy arithmetic in native code and releases the GIL, measured thread execution may also be viable.

The architecture should not create one blocking orchestration thread per semantic feature.

---

# 30. Workload Plugin Boundary

PiPy workloads are code and therefore a security boundary.

Initial versions may assume workloads are locally trusted Python packages installed by the operator. The cluster should not silently accept arbitrary executable code from an untrusted network peer.

A workload identity should include:

```text
package/name
version
algorithm identifier
schema version
code/package hash where practical
```

Before a job begins, participating nodes must establish that they have a compatible workload implementation.

Possible policies:

- require workload preinstallation on all participating nodes;
- automatically exclude incompatible nodes;
- later support authenticated package distribution as a separately designed feature.

Remote-code distribution is not required for the initial architecture.

---

# 31. Capability Matching

Nodes advertise capabilities through authenticated cluster state, not merely BLE advertisements.

Capabilities may include:

```text
architecture
CPU count
memory
optional GPU/accelerator
installed workload versions
available disk
native library capabilities
benchmark classes
```

A work unit can specify requirements.

The scheduler only leases work to eligible nodes.

This allows the fabric to remain useful beyond homogeneous Raspberry Pi fleets while retaining Raspberry Pi as the primary target.

---

# 32. Backpressure and Resource Limits

PiPy must remain stable when work generation exceeds immediate execution capacity.

The scheduler maintains a logical frontier rather than materializing millions of tiny queued Python objects when avoidable.

Mechanisms include:

- bounded local executor queues;
- dynamic work splitting;
- lease count limits per node;
- artifact storage quotas;
- state-log compaction;
- telemetry rate limits;
- bounded retry policies;
- pressure-aware chunk sizing.

The consensus leader should not become a memory bottleneck proportional to every possible future leaf in a huge job graph.

For recursive workloads such as binary splitting, the frontier may be generated lazily.

---

# 33. Exactly-Once State vs At-Least-Once Computation

PiPy does not require exactly-once physical execution.

In a failure-prone distributed system, a work unit may execute more than once.

PiPy instead aims for:

- **at-least-once opportunity for required computation**;
- **idempotent result identity**;
- **exactly-once authoritative acceptance of a logical result transition**.

Thus two nodes may compute the same unit after a lease race or partition. The replicated state accepts one valid logical result and recognizes the other as equivalent/duplicate.

This significantly simplifies failure recovery while preserving correctness.

---

# 34. Security Properties

PiPy should provide the following properties.

## Required

- no global static PiPy private key;
- cluster trust established by locally generated identities;
- each node has an independent persistent identity;
- admission requires explicit cluster-issued authority;
- BLE discovery alone grants no trust;
- replay-resistant admission handshake;
- forward-secret pairwise sessions where practical;
- unity-key material transported only over authenticated encrypted channels;
- Wi-Fi credentials transported only after authenticated admission;
- cluster identity continuity survives coordinator changes;
- expelled nodes can be excluded from future unity-key generations;
- protocol messages include versioning and domain separation;
- sensitive material is never emitted through UDP telemetry.

## Non-goals for initial versions

- defending against a root-compromised trusted cluster member executing arbitrary local code;
- Byzantine consensus among malicious authenticated members;
- anonymous Internet-wide federation;
- automatic secure distribution of arbitrary third-party workload code.

The initial fault model assumes members are trusted but machines and networks can fail. Security compromise and administrative expulsion are handled, but full Byzantine fault tolerance is outside the initial architecture.

---

# 35. Protocol Versioning

Every protocol family must be explicitly versioned:

- BLE discovery;
- admission handshake;
- cluster control messages;
- consensus state schema;
- work-unit schema;
- result schema;
- artifact metadata;
- telemetry.

Unknown required protocol versions should fail explicitly rather than be guessed.

Rolling upgrades should eventually support a bounded compatibility window, but correctness takes priority over indefinite backward compatibility.

---

# 36. Observability of the Cluster Itself

PiPy should expose enough information to explain its own behavior.

A node should be able to report:

- its node identity;
- cluster identity;
- current coordinator;
- term and membership epoch;
- peer health;
- unity-key generation number, but never the key;
- active jobs;
- local leased work;
- local throughput estimates;
- recent failures/retries;
- artifact/storage pressure;
- thermal throttling;
- election history sufficient for diagnosis.

Human-readable status should be derived from structured internal state rather than being the only representation of that state.

# 37. Reference Startup Scenario

## Node A

The operator installs PiPy and runs:

```bash
pipy begin
```

Node A:

1. generates its node identity;
2. listens/advertises over BLE;
3. finds no trusted cluster;
4. creates cluster `C`;
5. generates cluster `imapipy` key pair;
6. generates unity-key generation 1;
7. initializes one-node consensus state;
8. becomes coordinator;
9. generates `makemeapipy.sh`.

Node A is now a functioning one-node compute cluster.

## Node B

The operator copies/runs `makemeapipy.sh` on Node B.

Node B:

1. installs/configures PiPy;
2. stores cluster `C` public trust anchor and bounded enrollment capability;
3. generates its own node identity;
4. starts BLE discovery;
5. discovers Node A, or another member;
6. executes authenticated four-way admission;
7. receives membership and unity-key generation 1 over encrypted session;
8. optionally receives configured Wi-Fi credentials;
9. joins IP control plane;
10. synchronizes consensus state;
11. begins computing.

## Node C

Node C may discover Node B first.

That is valid. Node B can authenticate Node C’s enrollment capability and relay/admit it through the authoritative membership process. Node A need not be the radio peer that performs the bootstrap merely because Node A originated the cluster.

This property is central to self-organization.

---

# 38. Reference Failure Scenario

Suppose nodes A, B, C, D, and E are computing a π job. A is coordinator.

A fails.

```text
B/C/D/E miss coordinator heartbeats
    |
randomized election timeout
    |
one candidate obtains majority
    |   (if transient collision)
new election term
    |
C obtains majority
    |
C becomes coordinator
    |
replicated work frontier already present
    |
A's leases expire
    |
unfinished units return to available frontier
    |
B/D/E claim them
    |
π computation continues
```

If A later returns, it authenticates, observes the newer term, becomes a follower/compute node, synchronizes state, and resumes claiming work.

No permanent “master” recovery is needed.

# 39. Reference Dashboard Scenario

A laptop on the same LAN is not a PiPy member.

The user installs:

```bash
pip install pipy-dash
pipy-dash
```

The dashboard listens for `pipy.status.v1` UDP traffic and stores observations in SQLite.

It can display:

- cluster membership;
- coordinator changes;
- active π job;
- digits target;
- overall progress;
- per-node throughput;
- CPU/temperature;
- lease/work distribution;
- failures/retries;
- historical scaling behavior.

If the dashboard is stopped, deleted, or disconnected, computation continues unchanged.

# 40. Architectural Invariants

The following are intended to remain true even as implementation details evolve.

1. There is one PiPy node implementation, not permanent controller and worker products.
2. A one-node cluster is fully valid.
3. No globally shared static private “PiPy identity” exists.
4. New clusters generate their own `imapipy` identity.
5. Every node generates its own persistent node identity locally.
6. `makemeapipy.sh` grants bounded enrollment authority, not possession of the cluster root private key.
7. BLE is discovery/bootstrap transport, not trust by itself.
8. Admission establishes an authenticated encrypted channel before unity keys or network credentials are transferred.
9. Leadership is temporary and elected.
10. Every healthy node may compute.
11. Authoritative job/membership state is replicated.
12. Telemetry is non-authoritative and externally consumable.
13. Dashboarding is optional and out-of-process.
14. Work uses leases and can be reassigned after failure.
15. Physical duplicate computation is acceptable; logical result acceptance is idempotent.
16. Workloads define splitting, computation, verification, reduction, and finalization; the scheduler does not encode π-specific behavior.
17. CPU-heavy work cannot block cluster control-plane responsiveness.
18. Large artifacts do not belong in the consensus log merely because they are part of a job.
19. A known cluster member that temporarily loses contact does not create a new cluster.
20. Cluster operation after installation does not depend on Internet connectivity.

A practical first implementation can remain compact while preserving the architecture.

```text
    -> UDP telemetry
```

The architecture should be implemented as complete end-to-end slices rather than as disconnected infrastructure layers.

# 42. Package-Reuse Policy

PiPy should prefer established Python packages and system APIs over bespoke implementations when they satisfy the architecture.

Before implementing cryptography, BLE plumbing, consensus primitives, arbitrary-precision math helpers, serialization, or networking infrastructure from scratch, the implementation should evaluate maintained packages available through PyPI and existing operating-system facilities.

In particular, PiPy should not invent cryptographic primitives.

Bespoke code should focus on the parts that define PiPy itself:

- cluster lifecycle;
- membership semantics;
- self-organization policy;
- work model;
- adaptive leasing;
- replicated job state;
- workload interface;
- π decomposition/reduction integration;
- telemetry contract.

# 43. Final System Model

The complete conceptual system is:

```text
                         +----------------------+
                         |    optional tools    |
                         | pipy-dash / others   |
                         +----------^-----------+
                                    |
                             UDP telemetry
                                    |

      BLE discovery + authenticated admission + IP control plane

+----------------+     +----------------+     +----------------+
|    PiPy A      |<--->|    PiPy B      |<--->|    PiPy C      |
| identity       |     | identity       |     | identity       |
| discovery      |     | discovery      |     | discovery      |
| state replica  |     | state replica  |     | state replica  |
| scheduler      |     | scheduler      |     | scheduler      |
| compute        |     | compute        |     | compute        |
+-------+--------+     +-------+--------+     +-------+--------+
        \                     |                      /
         \                    |                     /
          +---------- consensus cluster -----------+
                             |
                      replicated jobs
                             |
                      leased work graph
                             |
                   deterministic results
                             |
                         reductions
                             |
                         final artifact
```

At any moment one member may be coordinator. That fact should be operationally important to the protocol and operationally unimportant to the user.

The desired user experience remains simple:

```bash
# first Pi
pipy begin

# generated by the first cluster
./makemeapipy.sh

# on any cluster member
pipy job submit pi --digits 1000000000
```

Everything between those commands—the discovery, trust establishment, membership, election, state replication, scheduling, compute distribution, recovery, reduction, and telemetry—is PiPy.
